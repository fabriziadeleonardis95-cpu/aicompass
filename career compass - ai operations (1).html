Technical Ladder — from vibe coding to agentic engineering
Below IC2
Vibe coding
Prompts an AI tool until something works. Does not read or understand the output. No version control, no tests, one-off scripts that break silently.
IC2
AI-assisted building
Reads and understands every line the AI writes. Uses Git, basic tests and error handling. Ships low-code and code workflows that others use.
IC3
Production automation (Judge)
Owns systems in production: deployment, secrets, retries, idempotency, logging, alerting, runbooks. Catches hallucinated APIs, wrong logic and security issues in AI output. Knows when to stop prompting and write it herself.
IC4
Agent design (Elevate, Design)
Designs LLM pipelines and agents: tool use, structured outputs, retrieval, human-in-the-loop. Builds evals, guardrails and LLM cost tracking before shipping. Writes specs, context files and prompt patterns others reuse. Makes adopt/kill calls on new capabilities, aligned with the Engineering Platform team.
IC5
Agentic engineering (Transform)
Agents write most of the code; she owns the spec, the architecture, the harness and the review. Work starts from a written spec, runs inside a harness, is blocked by eval gates, and every agent failure becomes a permanent fix to the harness. The AI team builds on her harness, designed with the Engineering Platform team on shared infrastructure (CI, secrets, permissions). Evidence below.
What agentic engineering (IC5) looks like in practice
ElementTangible evidenceHow to check
Spec before agentA spec template lives in the repo: problem, acceptance criteria written as testable statements, out of scope, data touched. Every agent-built change links to its spec. Each acceptance criterion maps to a test or an eval case. Work is cut so one agent run equals one reviewable PR.Pick 3 recently merged changes: each links a spec, and each acceptance criterion has a matching test or eval case.
Agent harnessContext files and skills are only the starting point. The harness is the infrastructure around the agent:
- Sandbox: agents run in an isolated container or dev environment, never on her laptop with her credentials, never against production.
- Scoped tools and credentials: an allowlist of tools per agent, read-only by default, write access only to its own branch.
- Policy hooks: forbidden actions are blocked before they run (pushing to main, reading secrets, deleting data, calling production APIs).
- Verification loop: the agent runs tests, linters and evals itself and iterates until green before it can open a PR.
- Budgets: token, time and cost limit per run, with automatic stop.
- Traces: every run is logged (prompt, tool calls, diff, cost) and can be replayed.
Built on the Engineering Platform team's shared infrastructure (CI, secrets manager, sandboxes).		Ask her to launch an agent on a real task and show: where it runs, a forbidden action being blocked, the verification loop going red then green, and the run trace with its cost.
Review she ownsAgent changes go through the same PR review as human code: branch protection, no direct push, agents never merge their own work. She can explain any merged module; anything she can't explain is rejected. High-risk paths (payments, customer messages, data deletion) need a second reviewer.Branch protection settings. Pick a random agent PR and have her walk through it.
Eval gatesCI blocks merge on failing tests, type checks, lint and security scans (secrets, dependencies). Each production agent has a versioned eval set built from real cases, including every past failure, run on every prompt, model or tool change. A score below baseline blocks the release. Prompts, model versions and agent configs live in version control, never edited directly in a vendor UI.Required checks in the CI config. Score history per agent. The prompt of any live agent can be found in the repo, with its change history.
Failures compoundEvery agent failure (rejected PR, incident, eval miss) gets an entry in a failure log: what happened, root cause, and the fix applied to the harness (new eval case, new hook rule, updated skill or context). The same failure never happens twice.Failure log entries linked to harness commits. Eval set and hook rules growing month over month. Zero repeat failures.
Event-triggered agentsAt least 2 agents start without a human: on a failed workflow, an alert, a ticket tagged agent-ready, or a schedule. They open a PR or a draft fix for her review, and never merge on their own.Run history showing each trigger and the PR it produced.
Measured like a serviceA monthly view per agent: share of changes merged without revision, time from trigger to PR, cost per run and per month, defects traced to agent changes. A written stop rule, for example pause an agent if its acceptance rate stays below 80% for 2 weeks or it goes over budget.The dashboard exists and is part of the monthly leadership report. The stop rule is documented, with its trigger history.
